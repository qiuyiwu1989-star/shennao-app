三处我上一版画错了

① 认知状态是三档，不是两档

epistemic 的取值是 attested 亲证 / inferred 推断 / conjecture 猜想。Api.kt 的注释：

必须显示——手机是一扫而过的场景，一条猜想会被当成事实。

② 「今天」是四件事，不是两件

到期承诺 + 新洞察 + 到期的预测 + 等着认人的（counts.awaitingSpeaker）。预测那一栏是竞品完全没有的东西——Prediction.observableSignal：「看到什么就算应验／落空」。

③ 台账应该按链路四站画

Stage：RECORDED → DELIVERED → TRANSCRIBED → ANALYZED，另有 FAILED（带 problem，服务端保证是人话）。上一版我自己编了「已入库/已跳过」，系统里本来就有更准的四站。

系统里已有、但手机上一直没露面的三样

  • Person.keptRate —— 人的兑现率。字段注释：「null = 还没有任何一条有结论。给 0% 或 100% 都是拿数字撒谎」。这是 L3 资产层最锋利的一屏，竞品全都没有。
  • MeetingAnalysis.methods[] + routingReason —— 这一场用了哪几个方法、为什么。这是深脑「方法可审计」的用户面，Plaud 的模板给不了。
  • recordings/[id]/marks + hotwords —— 标记与热词，服务端早就有。语音口令与 MARK 键落地时不用新建后端。

信息密度：一屏只让人做一个决定

「信息量不能太大」是这一版新加的硬约束，不是审美偏好。密度失控在这个产品里不是难看，是危险——《用户价值洞察》缺口 5 说手机是「一扫而过的场景」，Api.kt 说「一条猜想会被当成事实」。两句话指的是同一件事。

规则一 · 每区块只露一条

其余收成一行「还有 N 条 ›」。数字仍然给全——用户要知道有多少，但不必一次读完。「今天」四个区块全展开就是一堵墙。

规则二 · 猜想默认折叠

它信息量最大、最需要上下文、也最容易被当成事实。折叠态只给「猜想 N · 点开看它凭什么」。亲证与推断照常展开——那两档有原话托底。

规则三 · 一屏一个决定

出现两个并列主按钮就是超载的信号。次要动作降级为文字链或收进「···」。S7 的预测卡因此从三个按钮收成一个「去给个说法」，判断留给 S15。

验收：任意一屏在 360×780 的首屏内，需要用户读的正文不超过 5 条；超过就折叠。这条要在设计走查里逐屏过，不靠自觉。
