## 必须先处理的实现问题

### A1 / P0：断网被当成成功，可能删除唯一的本地音频（已复现）

位置：`Client.kt` 的 `UrlHttp.send`；`record/Uploader.kt:356-378`、`220-229`。

网络异常被统一转换为 `HttpResponse(0, ...)`。上传器的 PUT、complete、stop、finalize 只检查 `status >= 400`，所以 0 会进入成功分支；最后执行 `vault.deleteSession(session)`。

复现：建会话和 ticket 正常，之后模拟网络全部失败（状态 0）。实际得到 `DrainResult.Done`，本地会话目录被删除，音频没有成功 PUT。使用临时生成的 100 字节测试文件，没有接触用户录音。

建议：把传输异常与 HTTP 应答拆开；所有成功判断明确要求 2xx，仅对白名单中的幂等状态做额外处理。在服务端确认完整收尾之前保留本地音频。补充每一网络阶段的断网、超时、异常应答回归测试。

验收：ticket 后断网、上传确认前断网、stop/finalize 断网，都不能显示完成或删本地音频；恢复网络能继续完成。

### A2 / P1：分片传完但收尾失败，后台任务可能提前结束（已复现关键判据）

位置：`record/UploadWorker.kt:23-33`；`record/Resume.kt:44-46`。

Worker 丢弃 `Resume.kick()` 返回的各会话结果，只数 SEALED 分片。若音频全部变成 UPLOADED，但 stop/finalize 返回 503，Uploader 返回可重试失败且保留会话，`pending()` 却为 0，Worker 选择 success，不再按该任务退避重试。

两个探针分别复现 stop 503 和 finalize 503，均得到“可重试失败 + 本地会话仍在 + pending=0”。未在真实 WorkManager 调度器上运行整条链路；结论由复现的返回值及 Worker 的明确分支共同支持。再次打开 App 或其他触发可能恢复，但不能依赖用户主动回来。

建议：分别统计待传分片和待收尾会话，结合 DrainResult 决定是否重试；不可重试与需要重新登录的状态要给出可操作入口。

验收：全部分片传完后的收尾 503，在关闭页面的情况下仍能自动重试。

### A3 / P1：退出登录可以被正在进行的凭证刷新撤销（已复现）

位置：`Client.kt:127-142`、`524-539`。

`validAccessToken()` 有同步锁，`signOut()` 没有与之配套的代际校验。刷新先读取旧凭证并发请求，随后用户退出清空凭证，迟到的刷新响应仍然会写回旧账号的新凭证。

复现：用 CountDownLatch 暂停刷新响应，执行 signOut 并确认 store 为空，再放行响应；旧账号凭证被重新写入。全程仅本地假请求。

建议：为登录会话增加 generation / session epoch，在退出与切换账号时递增；异步响应写回前校验 generation。同步保护应避免让主线程等待网络请求结束。同时清理 WebView cookie、取消旧账号请求，并决定录音中的退出行为。

验收：刷新进行中退出后，旧响应不能恢复登录；切换账号/组织期间迟到请求不能覆盖新状态或写回旧缓存。

### A4 / P1：声明支持 Android 10/11，但缺少旧版蓝牙权限（静态确认）

位置：`app/src/main/AndroidManifest.xml:22-34`。

源码与本次构建的 merged manifest 都只有新 BLUETOOTH_SCAN / BLUETOOTH_CONNECT，没有旧 BLUETOOTH / BLUETOOTH_ADMIN。minSdk 29 表示仍支持 Android 10/11；这些系统需要旧权限。

建议：补充旧权限，并限定 maxSdkVersion=30；在 Android 10/11 真机验证扫描与连接。在 Android 12+ 验证新的运行时权限拒绝/重试路径。

依据：[Android 官方蓝牙权限说明](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)。未运行 Android 10/11 真机，不能声称已经观测到该设备上的报错。

### A5 / P2：失败记录缺少真正能走通的恢复入口（截图和源码确认）

位置：`HistoryScreen.kt:258-290`、`212-216`；`Demo.kt` 的 s4 数据。

当前截图中，“不到 5 分钟，默认不分析，要分析可以在详情里点一下”被显示为红色“没成功”。该夹具的 transcriptId=null，而点击详情依赖 transcriptId，实际只有删除入口。其他没有转写编号的记录也缺少独立详情页。

建议：记录详情以 sessionId 为入口，从本地保存到分析完成都可打开。明确区分“已保存但未分析”“上传失败”“转写失败”“分析失败”；按当前状态提供重试、手动分析、查看原因、本地导出。不要把业务规则跳过处理与失败混为一谈。

验收：每个状态都能打开详情；任何文案指向的按钮都存在且可操作，短录音不会只剩删除。

## 需要继续验证的会话边界

这些是代码风险，尚未做真实账号的跨账号实验，不等同于已发生泄漏。

- WebView 会通过一次性票据获取独立 cookie，但退出登录没有发现 CookieManager 清理逻辑。补充“打开网页版 → 退出账号 A → 登录账号 B → 再开网页版”的验证。
- 本地录音保留 orgId，但没有 userId；记录页直接扫描整个 recordings 目录，退出也不停止录音或隔离该目录。同组织不同用户在同一手机上换号时，本地待上传录音的展示、上传身份与处置需要明确。不要通过删除待上传音频来解决隔离问题。
- 定时聆听是通知提醒，不是自动开关录音；设置中已经说明这一点，应保留一致表述，并测试通知被拒绝、改时区、重启、错过提醒等行为。

## 产品与界面建议（设计判断）

### 第一轮：让人确定“录到了、存住了、下一步是什么”

将录音和全时聆听整理成一个采集控制面：本次录音 / 持续聆听两种清楚的模式；显示正在听、实际录制时长、本地待上传数、上传状态。定时计划与后台权限从这里可达，避免用户到“我的”里拼装功能。

保留清晰可见的录音状态、暂停/停止入口和录音前告知。把权限说明写成直接行动，不用让用户理解系统实现细节。

### 第二轮：记录默认按时间找，内容卡片作为另一种查看方式

现在双栏卡片的大段预览适合浏览内容，但压低标题、日期、时长的识别效率；失败行集中顶部，会持续抢占首屏。建议默认时间线单列：标题、时间、时长、来源、状态、一两行摘要；内容卡片作为可切换视图。异常有汇总入口，也能定位到原记录。

### 第三轮：先把每场录音的价值呈现完整，再扩大“今天”的判断流

“今天”目前强调承诺与逾期，对于先来录音、找纪要的人，打开后不容易确认刚才的录音去了哪里。建议先补“最近一次录音结果”和“待我处理”，承诺追踪保留但减少首屏负担。这是针对现有界面的建议，是否采用应结合用户主要场景决定。

### 文案统一

“下文”“没成”“灵魂卡”等词有个性，但新用户需要学习。建议关键状态用可预测的直白名称，例如“待跟进”“上传失败”“录音笔”；品牌名可并列保留。避免用同一个“没成功”概括不同处理阶段。

## 建议开发顺序与完成标准

1. **可靠性修复版**：A1、A2、A3优先；补蓝牙兼容权限。完成断网恢复、收尾重试、退出竞态回归。
2. **采集与记录体验版**：统一采集入口，建设 sessionId 详情页，所有失败状态提供对应操作。
3. **真实使用验收**：用户手机 + CB08，验证锁屏录音、来电打断、断网恢复、蓝牙断开重连、低存储、重启、换账号和覆盖升级保留数据。
4. **发布**：固定签名；校验 APK 版本/哈希与下载清单一致；从实际下载入口安装并完成一次录音到结果的闭环。

不建议同时重写协议层、重做全部 UI、升级所有依赖。先给最危险的场景加保护，保持每轮变更可验证。Lint 的多数提示是依赖版本和样式规范，不能用“全部升级”替代上面的可靠性工作。
